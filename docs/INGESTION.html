How a transcript becomes a searchable row

Five stages run between a coding agent appending a line to a log file and that line coming back out of cs search. The seam that matters sits in the middle: everything left of the archive is captured and never interpreted, everything right of it is derived and can be thrown away. This page walks the path, names the archivers that exist today, and measures what each one actually contributes to the index.

01

The path, end to end

The straight line is source → archive → importer → index → client. Each stage is allowed to know strictly less than you would expect, and that is the design: the archiver never parses content, and the importer never touches the filesystem. Those two restrictions are what make it possible to re-parse three years of transcripts against a better parser without re-collecting a byte.

1sources

Live, mutating files on disk

Agent CLIs append to their own transcript logs as they run. A source is defined as a watched location — a path plus a glob — never as a product or a surface (ADR 16). That is precisely the definition a server-side chat cannot satisfy, which is why claude.ai and ChatGPT-on-the-web are dark here until something lands their bytes in a watched directory (ADR 21).

~/.codex/sessions ~/.claude/projects ~/.gemini/tmp chatgpt export dir
2capture

cs archive — copies bytes, reads nothing

Scan each watched location and classify every file against the last observation: unchanged (size and mtime match — not even hashed), new, appended (grew with its first 64 KiB hashing the same), rewritten (prefix changed or the file shrank), vanished. Only the middle three copy anything. On APFS the copy is a clonefile reflink, so capturing a gigabyte costs almost no additional disk until the two sides diverge.

64 KiB prefix hash clonefile / FICLONE rewritten → _superseded/
3archive

The raw archive and its manifest durable

Bytes land at <root>/raw/<machine>/<source>/<rel_path>, mirroring the source tree. Alongside them, an append-only JSONL event log records every observation. The manifest holds the two facts nothing else can reconstruct — when a file was first seen, and when it vanished — which is exactly why it lives in the archive and not in the index (ADR 19).

raw/ · immutable manifest/*.jsonl 1,693 events
4import

One module per format, pure over bytes

An importer is a function of (logical_path, bytes) and nothing else. No database, no network, no reading a sibling file. It mints conversation identity, collects title candidates, and emits normalized Conversation records carrying a message DAG — parent edges and thread keys, not a flat list (ADR 4).

codex.rs claude_code.rs chatgpt_export.rs gemini.rs claude_desktop.rs
5index

cs index — always a full rebuild derived

The database file is deleted, not emptied, then rewritten from scratch in one transaction per source. Conversations fold together on their id; messages insert OR IGNORE; tool text is clipped to 1 KiB on the way in; postings go into one of two separate FTS5 tables. There are no migrations, because every column is a pure function of (archive, importer version).

index.db fts_prose fts_tools ~9 s full rebuild
The invariant the whole shape rests on

Every column in index.db must be a pure function of (archive, importer version). That is what makes rm index.db && cs index a valid answer to any schema change, and why the codebase has no migration path at all. Anything authored rather than derived — stars, notes, renames, the query log — belongs in a different file (ADR 1, ADR 3).

The two that do not reach the index

  • OpenCode is a capture problem. It is configured with layout = "bundle", and bundle capture has never been written, so the archiver walks past it. The reason it needs its own layout is scale: OpenCode stores roughly 170,000 fragment files averaging under 4 KB across session/, message/ and part/. Mirroring that 1:1 means re-walking 170k paths on every scan (ADR 18). Usefully, cs index prints the source with its reason rather than omitting it.
  • Claude Desktop is the mirror image — a config problem. The importer exists and works: it reads the Cowork and Chat tabs' local sessions, where one session is two files (a .json carrying the title and model, an audit.jsonl carrying the messages) that fold together on a shared native id. There is simply no [[sources]] block pointing at it. Aiming the existing claude-code glob at that directory is the tempting shortcut and is wrong — the files parse, but land under the wrong source id, carrying a claude --resume command that cannot reopen a desktop session, and without titles. A test pins that, because the failure looks like success.
Still dark, and no archiver can fix it

claude.ai, ChatGPT on the web, and Gemini on the web keep conversations server-side. They have no path, so under ADR 16 they cannot be sources at all. The accepted route is a fetcher that materializes export-shaped files into a watched directory — which keeps the archiver and the importers offline and pure — rather than network code inside either one (ADR 21). ChatGPT's local store is AES-256-GCM behind a Keychain access group and is not readable by anyone but OpenAI.

Two numbers in that table are worth stopping on

gemini-cli costs 175.8 MiB to contribute 120 messages. Of its 34 archived files, 15 are chat sessions and 15 are checkpoints/ — and the checkpoints are 175.5 MiB of the total, six of them 29 MiB apiece. claude-code's coverage starts 2026-06-17, not because that is when it was first used, but because Claude Code auto-deleted transcripts after 30 days until retention was raised. Everything earlier is gone upstream and unrecoverable — an archive can only ever be as old as its first capture.

04

What the index holds, and what it searches

Every message carries a kind, and kind decides everything downstream: how much text is stored, which FTS table gets the posting, and whether a query can reach it at all. Tool traffic is 68.3% of the rows and would flatten BM25 if it shared a table with prose, so it gets its own (ADR 5).

Rows by kind — 181,521 messages

Tool calls and results together are more than two thirds of the index by row count.

Stored text by kind — 105.6 MiB after clipping

Prose is under a quarter of the rows but 42% of the stored bytes, because tool text is truncated and prose is not.

Tool text is clipped on the way in

Tool output was dominating the database — 201 MB of tool_result and 40 MB of tool_call against 41 MB of prose. All of it is reproducible from the archive, so by ADR 1 none of it strictly has to be stored. But the head of a tool call earns its keep: it holds the tool name and the start of its arguments, which is what makes "which conversation ran cargo build" an answerable question.

So TOOL_TEXT_MAX is 1 KiB, applied before insert rather than at query time — the bytes never reach the database, and the FTS index only ever sees what is stored. Measured on this corpus that truncates 13.1% of tool calls and 44.7% of tool results. Truncation is marked in the text rather than silent, because a quietly shortened result reads as "the tool returned little", which is a different and more misleading claim than "there is more in the archive".

Reasoning is stored and deliberately not indexed

The posting counts confirm it exactly: 43,119 prose postings plus 124,034 tool postings is 167,153, against 181,521 messages. The 14,368-row difference is precisely the reasoning count. Those rows sit in message with their full text and carry no posting in either FTS table.

This is a decision, not an oversight, and it was measured before it was made: across 28 real logged queries the recall gain from indexing reasoning is exactly zero, because reasoning discusses work that also appears in prose. What it would add is process boilerplate — "preparing" 186 times, "summarizing" 169, "verifying" 155 — placed directly in BM25's way, which is the ADR 5 hazard the two-table split exists to avoid.

What remains open (chat-search-8mb) is not an indexing job but an honesty one: cs search will not return a conversation whose only hit is in reasoning, while cs explain reports exists: true for the same term, and the preview surface renders reasoning happily. Two surfaces disagree about whether something matched, and neither admits it.

05

Inside the index write

cs index opens a fresh database — the file is deleted rather than emptied, because DELETE FROM on a contentless FTS5 table fails once it holds rows, and CREATE TABLE IF NOT EXISTS will not add a column a newer schema introduced. Then, one source at a time, it reads every archived file, runs the matching importer, and writes the result in a single transaction. Accumulating per source rather than across all of them keeps peak memory at the largest source instead of the whole corpus.

Four behaviours worth knowing

  • Conversations merge; they do not overwrite. The upsert is COALESCE-based, so a conversation assembled from several transcript files keeps whichever file carried the title, cwd or model (ADR 7). This rebuild folded 95 conversations that arrived more than once and skipped 605 duplicate messages. A re-downloaded ChatGPT export re-delivers every conversation in the previous one; counting importer output rather than rows written once reported 4,022 conversations for a corpus of 2,011 — the dedup it looked like a failure of was working correctly the whole time.
  • A conversation is a DAG. Messages carry a parent edge and an explicit thread key. After insert, on_head_path is computed by walking parents back from each thread's leaf — per thread, not just from the conversation head, because a subagent thread runs parallel to the main one rather than being an abandoned branch. What it does catch is a superseded sibling from an edit-branch.
  • The FTS tables are external content over message. They store postings only and read text back by rowid, so this is the same bytes on disk as a contentless table — but fts5's highlight() becomes usable directly, where previously every message to be marked had to be re-inserted into a scratch table first. The consequence to remember when writing queries: an unconstrained scan of fts_prose returns every row of message. Only a MATCH consults the index.
  • A source that contributes nothing still gets a row in the report. Skipping it silently is how 2,011 ChatGPT conversations went missing from a run that reported success — an absent row reads as "no such source", which is indistinguishable from "nothing archived yet".

Where the 317 MiB goes

The message table is 62% of the file and its four indexes another 25%. The FTS postings — the thing the database exists for — are 39.5 MiB, or 12.5%. Storing message text at all is a convenience for snippets and highlighting rather than a requirement: every byte of it is reproducible from the archive.

06

The manifest, and what capture has seen

Change detection is a fold over an append-only event log, one file per month, stored inside the archive. It merges by concatenation, which is what makes it safe to sync across machines — a SQLite file in the same role is the corruption path the project explicitly avoids. Current state is derived; the log is the truth.

No file has been rewritten yet, so _superseded/ does not exist on disk. The append counts are the shape you would expect: claude-code transcripts are written to continuously, codex files are mostly closed by the time they are first seen, and both export sources are write-once.

One edge of this is drawn but not wired

Four claude-code files have vanished upstream. The tombstone column (deleted_upstream_at) exists in the schema for exactly this, but the fold from manifest into the index has not been built — so a vanished file's conversation currently looks identical to a live one. Deletion is meant to keep the data and make forgetting explicit (ADR 9); today it keeps the data and says nothing.

The one-line version

Capture bytes without understanding them; understand them without touching the disk; store the understanding somewhere you are willing to delete. Everything else in this document follows from those three.

Every figure on this page was measured on 2026-08-01 from a full cs index rebuild at importer version 4 — counts and byte sums queried from the resulting database, archive sizes from stat over raw/, event counts folded from manifest/*.jsonl. ADR numbers refer to docs/DECISIONS.md.
